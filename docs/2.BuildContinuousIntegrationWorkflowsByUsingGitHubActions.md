# Build continuous integration workflows by using GitHub Actions

*Continuous integration (CI)* is the process of using automation to build and test software each time a developer commits changes to version control in a code base. CI helps teams discover issues early in the development process and fix them quickly. You can use GitHub Actions to implement CI for code that you maintain in a GitHub repository.

<br><br>

## How do I use GitHub Actions to create workflows for CI?
### Create a workflow from a template
To create a workflow, it is common to begin by using a template:
    - On the main GitHub page navidate to **Actions** tab
    - Select **New workflow**
    - Use kaywords to find the desired set of temapltes that best match your goal (e.g. "Node.js")
    - Select **Configure** to use a template.

The **Node.js** template can look similar to this:

```yaml
name: Node.js CI

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

jobs:
  build:

    runs-on: ubuntu-latest

    strategy:
      matrix:
        node-version: [14.x, 16.x, 18.x]

    steps:
    - uses: actions/checkout@v3
    - name: Use Node.js ${{ matrix.node-version }}
      uses: actions/setup-node@v3
      with:
        node-version: ${{ matrix.node-version }}
        cache: 'npm'
    - run: npm ci
    - run: npm run build --if-present
    - run: npm test
```

> You specify that you want to test three versions of Node.js by using the `${{ matrix.node-version }}` attribute. This attribute references the matrix that you defined earlier. The cache attribute specifies a package manager for caching in the default directory.

<br><br><br>

### Implement reusable workflows

To use reusable workflows:
1. In your repository folder, create a reusable workflow. The file includes the automation steps you want to share, like common steps involved in testing, building, and deploying.
2. Explicitly enable a workflow to be reusable by configuring it with the workflow_call event.
3. In your main workflows (caller workflows), reference this reusable file and provide any required inputs or secrets.


<br><br><br>


### Customize workflow templates

You can further customize the previous template by adding more matrix paramters, for example see the introduction of additional OS type to the template:

```yaml
test:
    runs-on: ${{ matrix.os }}
    strategy:
        matrix:
            os: [ubuntu-latest, windows-latest]
            node-version: [16.x, 18.x]
        fail-fast: false
        max-parallel: 3
    steps:
    - uses: actions/checkout@v3
    - name: Use Node.js ${{ matrix.node-version }}
      uses: actions/setup-node@v3
      with:
        node-version: ${{ matrix.node-version}}
    - name: npm install and test
      run: |
        npm install
        npm test
      env:
        CI: true
```

> By adding `CI: true`, you are telling your test suites and build tools: "We are running on an automated server, so run non-interactively, fail fast if there's an issue, and keep the logs clean."

## Manage and debug workflows in GitHub Actions
Recall that your goal is to automate the code build and publish process so that features are updated each time a developer adds a change to the code base.

To implement this process, you learn how to:
- Identify the event triggered a workflow
- Use GitHub Actions workflow logs
- Save and access build artifacts
- Automate adding a label to a pull request after a review

<br>

### Identify the event that triggered a workflow
Types of triggers include a push to a branch, a pull request created or updated, a scheduled job, or a manual dispatch. 

#### What is a workflow trigger?
A workflow is an event that causes a workflow to run. Github supports various types of triggers, including:
- `push` or `pull_request` (based on code changes)
- `workflow_dispatch` (a manual trigger)
- `schedule` (cron job)
- `repository_dispatch` (external systems)
- Issues, discussion nad pull requests (for example, `issues.opened`, `pull_request.closed`)

#### Identify the trigger event
You can identify a workflow trigger event in multiple ways:
- **Use the GitHub Actions UI**:
  1. In your repository, select the Actions tab
  2. Select a workflow run
   
   And event type, such as `push`, `pull_request` or `workflow_dispatch` appears at the top of the workflow run summary.
- **Use `github.event_name` in the logs or in workflow**
  - GitHub exposes context data during a workflow run. The `github.event_name` variable tells you which event triggered the workflow.
  - You you can print the information in the step for debugging:
    
  ```yaml
  - name: Show event trigger
    run: echo "Triggered by ${{github.event_name }}"
  ```

- **Use workflow run details**
  - If you inspect workflow runs programmatically, such as by using API, the run object includes an `event` property that specifies the trigger.
  - You can find the commit Secure Hash Algorithm (SHA), actor and timestamp to trace what caused the trigger.

##### Trigger examples

```yaml
on:
  # 1. Push Event: Triggers on commits pushed to specific branches/tags
  push:
    branches: [ "main", "releases/**" ]
    tags: [ "v*.*.*" ]
    paths-ignore: [ 'docs/**', '*.md' ]
    paths:
      - 'frontend/**'        # Only runs if files inside the frontend folder change
      - 'package.json'       # Or if the root package.json changes

  # 2. Pull Request Event: Triggers when PRs are opened, synchronized, etc.
  pull_request:
    branches: [ "main" ]
    types: [ opened, synchronize, reopened ]
    paths:
      - 'frontend/**'        # Only runs if files inside the frontend folder change
      - 'package.json'       # Or if the root package.json changes

  # 3. Manual Trigger: Allows running it from the GitHub UI with custom inputs
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target environment to deploy to'
        required: true
        default: 'staging'
        type: choice
        options:
          - staging
          - production
      debug_mode:
        description: 'Enable verbose logging'
        required: false
        type: boolean
        default: false

  # 4. Schedule (Cron): Runs automatically on a time-based schedule
  schedule:
    - cron: '0 0 * * *' # Runs every day at midnight UTC

  # 5. Repository Dispatch: Triggers via external API / webhooks (cURL)
  repository_dispatch:
    types: [ custom_external_event ]

  # 6. Workflow Run: Triggers automatically after another workflow finishes
  workflow_run:
    workflows: ["Build and Test"]
    types:
      - completed

  # 7. Issue Event: Triggers when repository issues are modified
  issues:
    types: [ opened, edited, assigned ]

  # 8. Release Event: Triggers when a new GitHub release is published
  release:
    types: [ published, created ]
```


#### Work with artifacts
When a workflow produces something other than a log entry, the product is called an artifact. For example, the Node.js build produces a Docker container that can be deployed. The container is an artifact that you can upload to storage by using the [`actions/upload-artifact`](https://github.com/actions/upload-artifact) action. You can later download the artifact from storage by using [`actions/download-artifact`](https://github.com/actions/download-artifact).
Storing an artifact preserves it between jobs. Each job uses a fresh instance of a VM, so you can't reuse the artifact by saving it on the VM. If you need your artifact in a different job, you can upload the artifact to storage in one job, and download it for the other job.

```yaml
name: Build and Test

on:
  push:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install dependencies
        run: npm install
      - name: Build project
        run: npm run build  # This creates the /dist folder
      - name: Upload Build Artifact
        uses: actions/upload-artifact@v4
        with:
          name: build-files
          path: dist/
          retention-days: 5

  test:
    needs: build  # IMPORTANT: This ensures the build finishes before testing starts
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Download Build Artifact
        uses: actions/download-artifact@v4
        with:
          name: build-files
          path: dist/
          # This ensures it grabs the artifact specifically from the 'build' job
          run-id: ${{ needs.build.id }}
      - name: Install Test Dependencies
        run: npm install --production
      - name: Run Tests
        run: npm test
```

#### Automate reviews in GitHub by using workflows
Use `pull_request_review` to add an `approved` label when reviewer approves a pull request. This example uses the GitHub CLI, which is preinstalled on GitHub-hosted Ubuntu runners.

Create an `approved` label and save this workflow as `.github/workflows/label-approved.yaml` on the default branch. Test with new pull request from from branch in the same repo, approved by another user. You can't approve your own PR.

```yaml
name: Label approved pull requests

on:
  pull_request_review:
    types: [submitted]

permissions:
  issues: write
  pull-requests: write

jobs:
  label-approved:
    if: github.event.review.state == 'approved'
    runs-on: ubutu-latest
    steps:
      - name: Add approved label
        env:
          GH_TOKEN: ${{ github.token }}
          PR_NUMBER: ${{ github.event.pull_request.number }}
        run: gh pr edit "$PR_NUMBER" --add-label approved --repo "$GITHUB_REPOSITORY"
```

## Customize your workflow with environment variables

### Default environment variables and context
Within the GitHub Actions workflow, several default environment variables are available for you to use, but only within the runner that's executing a job. These default variables are case-sensitive, and they refer to configuration values for the system and for the current user. To use a default environment variable, specify $ followed by the environment variable's name.

<br>

In addition to default environment variables, you can use defined variables as contexts. Contexts and default variables are similar in that they both provide access to environment information, but they have some important differences. Although default environment variables can be used only within the runner, you can use context variables at any point in the workflow. For example, context variables allow you to run an `if` statement to evaluate an expression before the runner is executed.

```yaml
name: CI
on: push

jobs:
  prod-check:
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying to production server on branch $GITHUB_REF"
```

> The default environment variable $GITHUB_REF is used in the runner to refer to the branch. Notice that default environment variables are all uppercase where context variables are all lowercase.

##### How to Break Down Each Column
- **Workflow key**: The exact property path in your `.github/workflows/*.yml` file (e.g., global keys like `env`, job-level keys like `jobs.<job_id>.if`, or step-level keys like `jobs.<job_id>.steps.run`).
- **Context**: The allowed variable namespaces you can reference using expressions (`${{ ... }}`) at that exact line (e.g., `github`, `secrets`, `needs`, `matrix`, `env`). If a context isn't listed for a key, trying to use it will result in a syntax or evaluation error.
- **Special functions**: Any restricted built-in functions allowed at that location. Standard utility functions (like string manipulation) can be used anywhere, but powerful status functions (`always()`, `success()`) or file system checks (`hashFiles()`) are locked to specific keys.

#### Custom environment variables
Similar to using default environment variables, you can use custom environment variables in your workflow file. To create a custom variable, you need to define it in your workflow file using the env context. If you want to use the value of an environment variable inside a runner, you can use the runner operating system's normal method for reading environment variables. Also, you can define environment variables that are scoped to the entire workflow by using env at the top level of the workflow file.

```yaml
name: Greeting on variable day

on:
  workflow_dispatch

env:
  DAY_OF_WEEK: Monday

jobs:
  greeting_job:
    runs-on: ubuntu-latest
    env:
      Greeting: Hello
    steps:
      - name: "Say Hello Mona it's Monday"
        run: echo "$Greeting $First_Name. Today is $DAY_OF_WEEK!"
        env:
          First_Name: Mona
```


#### Use a default context in a workflow

The GitHub platform sets default environment variables. They aren't defined in a workflow, but you can use a default environment variable in a workflow in the appropriate context. Most of these variables, other than CI, begin with `GITHUB_*` or `RUNNER_*`. The latter two types can't be overwritten. Also, these default variables have a corresponding and similarly named context property. For instance, the `RUNNER_*` series of default variables have a matching context property of `runner.*`.
Here's an example of how to access default variables in a workflow by applying these methods:

```yaml
on: workflow_dispatch

jobs:
  if-Windows-else:
    runs-on: macos-latest
    steps:
      - name: condition 1
        if: runner.os == 'Windows'
        run: echo "The operating system on the runner is $env:RUNNER_OS."
      - name: condition 2
        if: runner.os != 'Windows'
        run: echo "The operating system on the runner is not Windows, it's $RUNNER_OS."
```

<br>

#### Pass custom environment variables to a workflow

You can pass custom environment variables from one step of a workflow job to subsequent steps within the job. Generate a value in one step of a job, and assign the value to an existing or new environment variable. 

```yaml
steps:
  - name: Set the value
    id: step_one
    run: |
      echo "action_state=yellow" >> "$GITHUB_ENV"
  - name: Use the value
    id: step_two
    run: |
      printf '%s\n' "$action_state" # This will output 'yellow'
```
